# Canonical config shapes

The literal target shapes `promote-project` scaffolds into a new or adopted repo.
These are the birth-time shapes; `project-maintenance` audits an existing repo
against the same conventions later, from its own copy.

---

## Agent-instruction file pointer

**`AGENTS.md` is the single source of truth.** It is the cross-tool standard
(read natively by Codex, Cursor, Copilot, opencode, Amp, and others).
`CLAUDE.md` and `GEMINI.md` are thin import pointers, never full copies.

Bare pointer (the common case - nothing tool-specific):

```text
@AGENTS.md
```

Pointer **with a platform-specific addendum** (the allowed exception). The
import line comes first; genuinely tool-specific rules follow below it:

```text
@AGENTS.md

## Common configurations
- Worktrees live under `.worktrees/`; reserve with a self-documenting `.worktree-reserved` marker, not a bare touch file.
- The on-save linter hook is configured in project settings, e.g. `.agents/settings.json`.
```

Claude Code and Gemini CLI auto-expand `@`-imports into context at launch
(relative path, max 4 hops). A plain markdown link (`See [AGENTS.md](AGENTS.md)`)
does **not** load; the guidance is then silently absent from most sessions.

Keep below the import line ONLY content that is meaningless to other agents:
harness-specific hooks/settings paths, the `Skill` tool, subagent `model:`
routing, `~/.claude/...`-style locations. Everything else - including
quality-gate docs (aislop), build/test commands, architecture notes, and
coding conventions - belongs in `AGENTS.md` itself.

## On-save linter hook

A `PostToolUse` Write|Edit hook that lints each file as it is written. For
Claude Code, add the following to `.claude/settings.json`. Canonical ruff +
shellcheck form:

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "f=$(jq -r '.tool_input.file_path // .tool_response.filePath // empty'); case \"$f\" in *.py) o=$(ruff check -q \"$f\" 2>/dev/null); [ -n \"$o\" ] && jq -n --arg c \"ruff:\\n$o\" '{hookSpecificOutput:{hookEventName:\"PostToolUse\",additionalContext:$c}}';; *.sh) o=$(shellcheck \"$f\" 2>/dev/null); [ -n \"$o\" ] && jq -n --arg c \"shellcheck:\\n$o\" '{hookSpecificOutput:{hookEventName:\"PostToolUse\",additionalContext:$c}}';; esac; exit 0"
          }
        ]
      }
    ]
  }
}
```

Repos with an aislop gate add a second hook entry of the same shape that runs
the pinned aislop binary. Pin the aislop binary version in a hook, never
`@latest` (a hook runs on every edit and `@latest` does a network check each
time). Tailor the `case` arms to the repo's actual languages.

When a hook command executes a script from the repository (e.g. with `node`,
`bash`, `python`, `pwsh`), always prefix the script path with
`"${CLAUDE_PROJECT_DIR}/"` (for example:
`node "${CLAUDE_PROJECT_DIR}/tools/hooks/post_tool_use.js"`). Cwd-relative script
paths break silently whenever a session working directory moves off the project
root.

The `.claude/AISLOP.md` and `.claude/CLAUDE.md` files that
`aislop hook install claude --project` generates stay gitignored and are
regenerated by the init script after a clean, never tracked:

```gitignore
.claude/*
!.claude/settings.json
```

## CI skeleton

Automates the validate tier (lint + format check + tests) so regressions
block at merge. Minimal lint skeleton (`.gitea/workflows/` for Gitea Actions;
`.github/workflows/` for GitHub-mirrored repos):

```yaml
name: lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install ruff
      - run: ruff check . && ruff format --check .
```

Scope paths explicitly (or rely on a root `pyproject.toml` `exclude`) so CI
does not run on generated/fixture trees.

## aislop quality gate

Language-agnostic AI-slop gate (deterministic, scored 0-100). Per-edit hook +
PR/CI gate. Target config (`.aislop/config.yml`):

```yaml
ci:
  failBelow: 80          # tune to the repo's current pass rate
exclude:
  - "*/workspace/**"     # generated / fixture trees
```

CI step (pin a version, never `@latest`): `npx --yes aislop@<ver> ci .` - use
the CLI on Gitea Actions, not the GitHub composite action. Disable
`python-formatting`/`python-linting` (ruff owns those). Known Python false
positive: `ai-slop/unused-import` fires on `from __future__ import annotations`
(do NOT remove that line). aislop scores the **whole repo** - there is no
diff-only mode.

## Post-clean init scripts

**The invariant:** `git clean -ffxd` must always be safe to run. Nothing
unrecoverable lives in the working tree: every file is either tracked and
pushed, or reproducible by re-running a tool. Two things do not come back on
their own after a clean: package restore, and the agent-instruction files the
aislop installer generates. `init.ps1`, `init.bat`, and `init.sh` at the
repository root restore a checkout to a working state. Every init script must
be idempotent (safe to run twice with no worse outcome the second time) and
cover every step below, since a partial script leaves the checkout stuck
between "cleaned" and "restored".

**Each of `init.ps1` / `init.sh`**, in order:

1. **Prerequisite check.** Report what is missing; do not install anything.
   Include the package manager / SDK, any platform-specific build tooling,
   and `aislop` (report its version if present, a missing-tool hint if not).
2. **Package restore.** Whatever the stack's dependency-restore step is.
3. **`aislop hook install claude --project`**, skipped with a hint when
   `aislop` is not on PATH. This regenerates `.claude/AISLOP.md` and
   `.claude/CLAUDE.md`.
4. **Settings line-ending normalization guard.** The installer rewrites the
   tracked `.claude/settings.json` with LF endings, which can leave
   `git status` reporting it modified with no content diff. Restore the file
   only when both ordinary `git diff --quiet -- .claude/settings.json` and
   staged `git diff --cached --quiet -- .claude/settings.json` are clean but
   `git status --porcelain -- .claude/settings.json` is non-empty - never
   when there is a real content change.
5. **Optional provisioner call.** If a settings-provisioning tool is on
   PATH, call it by a feature name (never its bare pipeline command) to
   re-apply the project-scope settings a clean removed, skipping silently
   when the tool is absent.
6. **Optional build.** `-Build` (PowerShell) / `--build` (bash), off by
   default to keep the script fast.
7. **Completed/missing summary.** Print what ran and what prerequisites are
   still missing.

**`init.bat`** is a thin forwarder, not a reimplementation: resolve `pwsh`
(fall back to Windows PowerShell), forward every argument to `init.ps1`, and
propagate its exit code. This is required, not optional - `cmd.exe` cannot
invoke `init.ps1` directly, so without the forwarder the documented recovery
path silently does nothing under `cmd.exe`: it reports the file "not
recognized" and the shell moves on, with no restore step ever running.

**`.gitattributes` eol rules:**

```gitattributes
# Shell scripts must check out with LF on every platform. With CRLF endings a
# script fails on Linux at the shebang: "bad interpreter: /usr/bin/env bash^M".
*.sh text eol=lf

# Batch files must check out with CRLF. cmd.exe tolerates LF for simple
# line-by-line scripts, but mis-parses labels, goto targets, and multi-line
# blocks, so an LF-only .bat works until someone adds one and then fails in a
# way that reads as a logic bug rather than a line-ending problem.
*.bat text eol=crlf
*.cmd text eol=crlf
```

**AGENTS.md "Cleaning the working tree" section**, built for the target repo:

1. **The invariant paragraph** - `git clean -ffxd` must always be safe to
   run, and why an exclude list would defeat the point of cleaning (git also
   offers no mechanism to protect a file from `clean`).
2. **A Removed/Restored-by table** built from this repo's own
   `git clean -n -ffxd` output, not copied from another repo - build-output
   directories and generated-file names differ by stack.
3. **The per-platform "getting back to work" invocation**: PowerShell
   (`./init.ps1`), `cmd.exe` (`init.bat`, noting the `.\` prefix a machine
   with `NoDefaultCurrentDirectoryInExePath=1` set requires), and bash
   (`./init.sh`).
4. **The provisioner paragraph** - what the optional settings-provisioning
   call does and why it is safe to skip when the tool is absent.
5. **The prerequisites line** - what each script checks for but does not
   install, per platform.
